# Timelines

Purpose: real durations, so promised timelines can be met. This project is a rehearsal; nothing is sold yet. Add one row per PR when it merges, and one row per incident that cost time.

## How to read the numbers

- **Work (upper bound):** time from the previous PR being opened to this one being opened. Work here was sequential, so this bounds the effort behind the PR. It includes reviews, questions and side tasks, so it overstates pure coding time. Gaps over 3 hours (breaks, nights) show `n/a`. When several PRs were prepared together and opened minutes apart, the later ones show too little; #7 to #11 (re-openings of #2 to #6) are left out.
- **Open to merge:** the wait for CI and auto-merge once the PR existed. It was measured from GitHub timestamps (UTC).
- **Incidents:** time lost to problems, measured from logs where marked "measured", otherwise an estimate and marked so.

## Estimating from this

- The per-PR work figures understate real effort where several PRs were prepared together (for example #44 shows 16m but built on work done alongside #43), and they include no time for the incidents below. Quote from the median plus the incident budgets, not the median alone.
- A small CI or workflow fix took minutes to under an hour of work, but its first real run often found a problem (registry, disk, quota). Budget one extra round for anything that runs only in a release.
- Anything new to the registry (a new package, a large image) failed on its first try twice. Budget a retry.
- A user-visible bug can sit unseen for hours without an end-to-end check; budget that check per release.
- Shared limits stop all work at once: Actions minutes and AI usage limits. Track them like any other dependency.
